# SDD 流程与风险评估（通用）

## SDD 规范（profile flags.sdd_required=on 的新功能强制）

1. **Spec 阶段** — PM 编写 Spec 到 profile.spec_dir，只定义「做什么/不做什么」与可验证验收标准
2. **Design 阶段** — 架构师基于 Spec 编写 Design，不质疑 Spec、不增删需求
3. **交接规范** — Spec 是 PM → 架构师的唯一交接物，交接前必须完成检查清单
4. **边界规则** — "不做什么"比"做什么"更重要；Spec 阶段不讨论技术方案；Design 阶段不改需求
5. **归档机制** — 完成后 Spec+Design 成对移入 profile.archive_dir

## 实施方案前必须风险评估

任何非平凡变更（>1 小时或 >1 个文件）在实施前必须完成风险评估：

- 🟢 可控风险 — 记录应对措施
- 🟡 弱可控风险 — 记录应对措施
- 🔴 不可控风险 — 记录接受条件

风险条目必须精确到 `文件:行号`，禁止"可能影响性能"式空话。

## 代码精简，注释标准化

在满足质量要求的基线上代码保持最精简，但注释和文档不能精简：

- 公共函数/组件必须有类型/用途注释
- 复杂逻辑必须说明"为什么"（而非"是什么"）
- 文档模板中的章节不可省略
- 注释语言以 profile.comment_language 为准（默认中文）

## 基线行为对齐（profile flags.alignment_check=on 时生效）

适用于重写/迁移类项目（如 v4→v5）：基线行为是唯一需求标准，禁止脑补。

1. **先查文档** — 实施前查 docs_dir 中是否已记录对应基线行为
2. **标注对齐点** — 对齐的设计/代码/提交必须标注「对齐: <功能点>」
3. **差异显式列出** — 与基线行为的任何差异（即使是"改进"）必须在 Design/Spec 显式列出并经用户确认
4. **存疑路径** — 无记录 → 列入「待确认问题」上报，用户确认前不得实现该分支
5. **复盘沉淀** — 新确认的基线行为写入 pm-memory 或行为文档，供后续对齐复用
