# Doc Writer — 文档撰写 Skill

## 使用时机

1. PM 编写 Spec（feature-dev 的 Spec 阶段）
2. 架构师编写 Design（feature-dev 的 Design 阶段）
3. 架构师编写多方案/评估文档（design-doc / design-eval / 技术调研）

## 通用纪律

- 输出目录取 profile 的 `spec_dir`（默认 `docs/specs/`）；完成后成对归档到 `archive_dir`
- 章节不可省略（本项目文档结构即审查对象，critic 会核对）
- 命名/术语先 grep 全库统计，跟随多数派
- 引用的函数/文件/行号必须实际存在（写之前 grep，不是写之后）
- 风险必须精确到 `文件:行号`，禁止"可能会影响性能"式空话

## Spec 结构（做什么层，禁技术方案）

```markdown
# <功能名> Spec
## 背景与目标
## 做什么        # 功能点清单 + 每条可验证的验收标准
## 不做什么      # 边界清单（比"做什么"更重要）
## 行为对齐      # alignment_check=on：对应基线功能点 + 显式差异清单
## 待确认问题    # 不自行假设，列出让用户定夺
```

## Design 结构（怎么做层，禁增删需求）

```markdown
# <功能名> Design
## 概述与输入 Spec
## 架构设计      # 模块划分、接口契约、数据流/事件流（引用点先 grep 核实）
## 代码落点      # 每项改动 → 实际文件路径（对照 profile 代码落点表）
## 阶段拆解      # Phase 1/2/3，含预估与前置依赖
## 风险评估      # 三类：🟢可控(记应对措施) 🟡弱可控(记应对措施) 🔴不可控(记接受条件)，精确到文件:行号
## 交接检查清单  # Spec 覆盖度自检（逐条对照），未过不得进入实施
```

## 多方案 / solution 结构（design-doc / design-eval / 调研）

```markdown
# <主题> 方案
## 执行摘要（1 句话）
## 现状分析
## 候选方案（≥3 套可区分，禁止换皮）  # 每套：改动范围/兼容性/成本/收益/潜在风险
## 详细设计（推荐方案）
## 阶段拆解
## 风险评估（三类 🟢🟡🔴）
## ROI 对比表（多方案横向）
## 不做清单
## 关键文件速查表
```

## 写作红线

1. Spec 阶段不讨论技术方案；Design 阶段不增删需求
2. "不做什么"必须写，防止范围蔓延
3. 不确定的基线行为/需求 → 列入「待确认问题」上报，禁止脑补拍板
4. 文档即交接物：下游角色只依赖文档，不口头传递
